# 음향·되묻기 보정 TODO

콜록의 음향 지표와 되묻기 탐지에는 실측으로 보정되지 않은 상수가 여러 개 있다. 이 문서는
2026-08-13 실기기 검증에서 드러난 문제를 근거와 함께 남기고, 각각을 어떻게 측정 가능한
작업으로 바꿀지 정리한다.

작업 원칙은 하나다. **숫자를 바꾸기 전에 측정 수단을 먼저 만든다.** 라벨 없이 상수만 갈아
끼우면 이번에 잡히던 것이 다음에 안 잡히고, 무엇이 나아졌는지 말할 수 없다.

## 0. 공통 규칙

- 품질 게이트나 detector 상수를 바꾸면 `ACOUSTIC_ANALYZER_VERSION`을 함께 올린다. 저장된
  값이 어떤 상수로 계산됐는지 구분되지 않으면 기준선 비교가 무의미해진다.
- 검증되지 않은 지표를 의학적 의미가 있는 것처럼 표시하거나 발표하지 않는다.
- 상수는 코드에 두지 않고 `Settings`에 노출한다. 보이지 않는 값은 틀렸다는 사실도 드러나지
  않는다.

## 1. `COUGH_EVENTS` 재현율이 사실상 0 (최우선)

### 증상

실기기 통화에서 기침을 두 번 했는데 `COUGH_EVENTS = 0.0`, 상태는 `OK`로 저장됐다.

### 근거

TTS 음원에 광대역 폭발음을 합성해 넣고 `_cough_candidates`를 직접 호출했다.

| 삽입 신호 | 탐지 |
|---|---|
| 없음 | 0회 |
| +6 dB / 0.3초 × 2 | 0회 |
| +20 dB / 0.3초 × 2 | 0회 |
| +30 dB / 0.3초 × 2 | 0회 |
| +40 dB / 0.3초 × 2 | 0회 |

+30 dB 폭발음이 들어간 프레임의 점수를 분해하면 다음과 같다. 임계값은 0.65다.

| 항목 | 점수 | 가중치 | 기여 |
|---|---|---|---|
| high (1 kHz 이상 비율 0.703) | 1.00 | 0.25 | 0.250 |
| zcr (0.229) | 0.90 | 0.20 | 0.181 |
| energy | 0.22 | 0.40 | 0.089 |
| crest (2.20) | 0.00 | 0.15 | 0.000 |
| **합계** | | | **0.520** |

### 원인

- **분석 창이 0.96초로 기침 길이(약 0.3초)의 세 배다.** 짧은 폭발이 긴 프레임에 평균되어
  에너지가 희석된다. `energy_score = (dB - median - 6) / 18`은 median 대비 24 dB 초과를
  요구하는데, 희석 때문에 10 dB 남짓밖에 오르지 않는다.
- **crest를 같은 프레임 안에서 `max / rms`로 계산한다.** 기침이 들어오면 분자와 분모가 함께
  커져 비율이 거의 변하지 않는다. 기준이 `(crest - 3) / 8`이라 3 미만은 전부 0이 되고,
  통화 중 기침에서는 원리적으로 이 항이 반응할 수 없다.
- 두 항의 가중치 합이 0.55다. 나머지 0.45를 만점 받아도 0.65에 도달하지 못한다. 즉 현재
  임계값은 **도달 불가능한 값**이다.

### 해야 할 일

1. `UNMEASURABLE` 반환 또는 지표 노출 중단을 기본값으로 둔다. `0.0 OK`는 "기침이 없었다"로
   읽히고 기준선에 0이 쌓여 이후 실제 기침을 이상치로 만든다.
2. 라벨 데이터를 모은다. 기침 30개, hard negative 30개(문 닫힘, 옷 스침, 웃음, 헛기침,
   자음 파열음). 실제 건강정보가 아닌 수집 동의된 샘플만 쓴다.
3. 아래 calibration harness로 파라미터를 sweep한다. 최소한 프레임 길이, hop, crest 정의,
   energy 기준선(median → 발화 제외 배경)을 후보에 넣는다.
4. heuristic은 현재 validation 실패로 간주한다. HeAR `event_detector_small`을 주 후보,
   YAMNet을 baseline으로 같은 in-domain label set에서 비교한다. full `google/hear-pytorch`는
   embedding model이라 cough count 경로에 직접 쓰지 않는다. 상세 판정은
   `voice-health-model-research.md`에 있다.

### 완료 기준

라벨 세트에서 precision/recall을 수치로 제시할 수 있고, 그 값이 문서에 기록되어 있을 것.

## 2. calibration harness (`scripts/calibrate_acoustics.py`, 미구현)

`scripts/evaluate_extraction.py`가 LLM 추출에 대해 하는 일을 음향 지표에 대해 하는 도구가
없다. 그래서 "고쳤다"를 주장할 방법이 없다.

필요한 기능:

- 라벨 fixture(`evals/cough_cases.json` 등)를 읽어 파일별 정답 이벤트 시각을 가진다.
- detector 파라미터를 격자 탐색하고 각 조합의 precision/recall/F1을 계산한다.
- 현재 설정값의 성적을 함께 출력해 회귀를 알 수 있게 한다.
- 결과를 JSON으로 남겨 문서에 인용할 수 있게 한다.

동일한 harness를 되묻기 탐지(4번)에도 재사용할 수 있어야 한다.

## 3. `PAUSE_RATIO`가 구조적으로 0

### 증상

TTS 음원과 실기기 통화 모두에서 항상 `0.0`이 나온다.

### 원인

`_pause_ratio`는 **한 segment 안의 단어 사이 간격**만 센다. 그런데 Deepgram은 쉬는 지점에서
segment를 나눈다. 실제 휴지는 대부분 segment 경계로 이동해 계산에서 빠진다.

### 해야 할 일

segment 경계를 가로지르는 간격을 포함할지 결정한다. 이는 지표 정의 변경이므로 기준선
비교 대상이 바뀐다. 팀 결정이 필요하고, 바꾸면 analyzer version을 올린다.

## 4. 되묻기 탐지의 재현율 미측정

`repeat-ko-v2`에서 오탐 하나를 고쳤다. `clarify.huh-eo`가 `어` 부분 일치로 "어지럽습니다"를
되묻기로 잡던 문제였고, standalone 규칙이 발화 전체를 덮을 때만 인정하도록 바꿨다.

하지만 **재현율은 한 번도 측정된 적이 없다.** 손으로 쓴 정규식이 실제 노인 발화의 되묻기를
얼마나 놓치는지 모른다. 라벨 세트를 만들어 precision/recall을 측정하고, 규칙 확장 또는 LLM
보조 분류를 검토한다.

## 5. `F0_VARIATION`의 유성음 게이트

실기기 통화에서 `INSUFFICIENT_VOICED_AUDIO`로 측정 실패했다. 조건은 다음과 같다.

```python
mask = voiced & isfinite(f0) & (probability >= 0.8)
if valid.size * 256 / sample_rate < 2:   # 유성음 2초 미만
```

`probability >= 0.8`과 `2초`가 모두 코드에 박힌 임의값이다. pYIN에서 0.5~0.6이 흔히 쓰이는
값이라 0.8은 보수적일 수 있다. 16초 발화에서 유성음 2초를 못 채우는 것이 정상인지 먼저
확인해야 한다. 두 값을 `Settings`로 올리고 실제 유성음 길이 분포를 측정한다.

## 6. 품질 게이트의 표본이 부족하다

2026-08-13에 `quality_min_active_dbfs`를 -45 → -55 dBFS로, `quality_active_percentile`을
75 → 90으로 조정했다. 근거는 실기기 실측이다.

```
peak  -30.4 dBFS
rms   -49.8 dBFS
p75   -48.0 dBFS
p90   -45.7 dBFS   ← 기존 임계값 -45.0에 0.7 dB 차이로 탈락
```

발화 프레임 레벨이 -46 dBFS 부근이라 10 dB 여유를 두고 -55로 정했다. 진짜 무음이나 마이크
차단은 -70 dBFS 이하로 떨어지므로 여전히 걸러진다.

다만 **표본은 iPhone 15 Pro 한 대, 통화 3건이다.** 기기·거리·환경이 다르면 분포가 달라진다.
`scripts/acoustic_quality_report.py`로 실패 사유 분포를 계속 관찰하고, 다른 기기가 붙으면
다시 확인한다.

## 7. `parent_min_speech_seconds = 20`의 근거

통계적 안정성 근거 없이 정해진 값이다. 발화 길이별로 지표의 분산이 어떻게 변하는지 측정해
결정해야 한다. 현재 개발 환경에서는 반복 검증을 위해 8초로 낮춰 두었다.

## 8. 녹음 시작 지연 의심 (확인 필요)

2026-08-13 통화에서 대본의 첫 문장이 전사에 나타나지 않았다. 분석용 PCM writer는
`마이크 publish 완료` 이후에 부착되므로, 통화를 받자마자 말하면 앞부분이 유실될 수 있다.

의도한 대본과 실제 전사를 비교하는 방식으로 재현 여부를 먼저 확인한다. 재현되면 writer
부착 시점을 앞당기거나, publish 이전 구간을 버퍼링하는 방법을 검토한다. 통화 앞부분이
항상 유실된다면 기침을 포함한 모든 지표에 영향을 준다.
